# Overengineering examples

Use these examples to inspect the whole operation and compare it with a simpler
design that meets the same current requirements. The scenarios and refactoring
advice below apply the linked sources to code review. Confirm requirements and
callers before changing code.

| Example and warning signs | Simpler design to compare | Requirements that can justify the mechanism |
| --- | --- | --- |
| **Task queues and workflow engines around a direct operation.** A caller needs a result, but the implementation adds job IDs, workers, status storage, polling, and retry scheduling. Being asynchronous, slow, or multi-step alone does not require this machinery. | Call and await the operation, use a fixed sequence for fixed steps, and reuse existing concurrency facilities. | Work must survive a restart, be delivered later, reach independent consumers, or satisfy defined ordering or backpressure. Examine backlog and recovery costs. [AWS: queue backlogs](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf). |
| **Speculative extension frameworks.** Plugin registries, provider interfaces, factories, configurable strategies, or a custom DSL support imagined backends and modes. Extra options make the current implementation harder to follow. | Implement supported cases with concrete code and existing framework facilities. Add extension points when a supported use needs them. | An existing consumer needs substitution or configuration, or the abstraction hides complexity and makes current callers simpler. One implementation alone does not prove an abstraction is unnecessary. [Fowler: YAGNI](https://martinfowler.com/bliki/Yagni.html). |
| **A shared abstraction that accumulates mode flags.** Different callers pass more switches and parameters to select unrelated branches. Changes to one case disturb others, while the shared code no longer expresses a common operation. | Inline the affected logic into its callers, remove irrelevant branches, then share only the behavior that is actually common. | The cases share a coherent domain operation and the interface hides their implementation without making callers manage the differences. [Sandi Metz: The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction). |
| **Premature service boundaries.** Components maintained and deployed together gain network APIs, serialization, remote failure handling, deployment coordination, and consistency problems without needing independent operation. | Keep clear module boundaries within one application. | Current team ownership, independent deployment, or scaling requirements justify the distributed system's additional work. [Fowler: Microservice Premium](https://martinfowler.com/bliki/MicroservicePremium.html). |
| **CQRS or event sourcing for ordinary current-state data.** Simple reads and writes gain separate models, command dispatch, projections, replay, and event schema maintenance. CQRS and event sourcing are separate choices; one does not require the other. | Use a shared model and ordinary transactions. Store required history directly without making every operation depend on replay. | Distinct read/write workloads or domain models need CQRS; required historical reconstruction or event-based domain behavior may justify event sourcing. Preserve deployed formats and data during a migration. [Fowler: CQRS](https://martinfowler.com/bliki/CQRS.html), [Microsoft: Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing). |
| **Caches and duplicate state without a performance need.** Cheap or rarely reused values gain expiration, invalidation, synchronization, and another service to operate. | Read or derive from one authoritative source, or use an existing cache that meets the need. | Supported latency, cost, or availability needs justify caching; data is reusable and the freshness contract permits it. An existing cache may already be necessary for current load, so check before removal. [AWS: caching tradeoffs](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/). |
| **Stacked recovery layers.** Every wrapper retries, translates errors, adds fallback state, or duplicates behavior already supplied by the client library. Retrying at several levels multiplies attempts and can repeat side effects. | Propagate errors clearly. Use the existing client's facilities and handle recovery where the caller can decide what to do. | Supported transient failures need bounded recovery, with one clear owner for retry decisions and defined idempotency and side effects. Keep required timeouts and external failure handling. [AWS: timeouts and retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/). |
| **Copied process machinery.** Extra inventories, approval files, reports, or repeated review gates imitate another project's workflow without supporting a decision, requirement, or risk in this task. | Perform the requested work and its relevant checks. Keep only records people need to use or maintain it. | A user requirement, external obligation, or actual approval boundary calls for the process. Preserve those commitments. [Steve McConnell: Cargo Cult Software Engineering](https://stevemcconnell.com/articles/cargo-cult-software-engineering/). |

A mechanism can create work that makes it appear necessary. An unnecessary queue
needs payload serialization, job state, recovery rules, status APIs, and tests for
those paths. Those pieces justify one another without establishing a need for the
queue. Trace the chain back to the original operation, migrate callers to the
simpler path, and remove code and dependencies used only by the discarded design.
Preserve required ordering, concurrency limits, cancellation, errors, and data.

The prohibition on AI-invented evidence layers in
[the skill](../SKILL.md#remove-invented-evidence-layers) still applies. Generated
callers, tests, or documents do not make those layers acceptable.
